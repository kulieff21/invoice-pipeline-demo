§1The job

Pay what is right, hold what is not

Supplier invoices arrive as PDFs: some generated by an accounting system, some scanned on an office copier. Accounts payable wants them as rows in a spreadsheet, and above all wants to know which ones not to pay yet.

Received

  • A folder of invoice PDFs, any layout, in six languages
  • Scans with skew, noise and lost characters
  • Re-sent copies, typos, sums that do not add up

Delivered

  • Google Sheet invoices: one row each, with status, issues, notes
  • Google Sheet line_items
  • A run report and a review queue (CSV)
§2How it reads

Six stations, one transaction per file

The pipeline can be stopped at any moment and started again: files already read are skipped by their bytes, and every sheet write is an upsert by key.

InboxSame bytes twice: skipped.
ReadText layer, or OCR with deskew.
ExtractLabels in six languages.
ValidateArithmetic, dates, check digits.
RecordSQLite, one transaction.
SheetKeyed upserts, retried.

Labels, not coordinates

A value is found to the right of its label, below it, or inside the same run of text (Fattura n. 2026/0147). Line items are read from the right, so descriptions may contain numbers and wrap.

The invoice checks itself

When a scan loses a decimal separator (15843), the value is repaired only if qty × price = amount then holds exactly, and the repair is noted in the row. A vendor’s own error is never corrected, only reported.

Two readers for scans

OCR and an LLM read the same page. Agreement is taken, a check digit or the arithmetic settles disagreement, and anything left goes to a person as READERS_DISAGREE.

§3Test data

Nine layouts, none of them real

Fictional companies, generated tax IDs with real check digits, a seeded generator in the repository. A quarter of the pages are rasterised like an office scanner. Some carry exactly one planted defect, so every detection can be scored. Click a page to read it.

§5Second reader

An LLM that is not trusted alone

35 scan pages that failed validation went to openai/gpt-6-luna through OpenRouter. It read the currency symbols the OCR could not, and it dropped repeated digits: 10597 became 1059, and one invoice reached the sheet as “ok” with the wrong number. §6Crashes

Kill it. Run it again.

The dangerous failure is a write that succeeded on the server whose response never arrived: a naive retry appends the rows twice. Every retry here re-reads the sheet’s keys and updates in place. The test below kills the pipeline 5 times at arbitrary moments and makes it die 6 times right after a write, before it can record it. This is the transcript of a real run.

§8Limits

  

    
What this does not prove

    
    
      
  1. The layouts are synthetic and written by the same person as the rules. Real vendors bring logos, stamps, handwriting and multi-page tables.
    2. 
      
  2. After a holdout was measured and fixed, its numbers are on seen data. Only the first-sight numbers are a test.
    3. 
      
  3. One page per invoice, one writer per spreadsheet.
    4. 
      
  4. Tax IDs are checked by check digit or format, not looked up in a registry such as VIES.
    5. 
      
  5. OCR runs on CPU, about six seconds per page, and drops £, €, some umlauts and many spaces.
    6. 
      
  6. The LLM cost is for this data, this model and one day's prices.
