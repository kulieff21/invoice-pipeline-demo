Invoice PDFs to Google Sheets, without silent errors

Reads generated PDFs and scans in six languages, checks every invoice against business rules and the vendor's tax-ID check digit, and writes rows that survive crashes, retries and re-runs. When it cannot read something with certainty, it says so and leaves the invoice to a person.

The job

Supplier invoices arrive as PDFs: some generated by an accounting system, some scanned on an office copier. Accounts payable wants them as rows in a spreadsheet, and above all wants to know which ones not to pay yet.

InputOutput
A folder of invoice PDFs, any layout, some scannedGoogle Sheet invoices: one row per invoice with status, issues, notes
Re-sent copies, typos, arithmetic that does not add upGoogle Sheet line_items, a run report and a review queue (CSV)

How it works

Six stages. Every file is processed in one database transaction, and every sheet write is a keyed upsert, so the whole thing can be stopped at any moment and run again.

01InboxSame bytes twice: skipped.
02ReadText layer, or OCR with deskew for scans.
03ExtractLabels in six languages, not template coordinates.
04ValidateArithmetic, dates, tax-ID check digits, duplicates.
05State + outboxSQLite, one transaction per file.
06Google SheetsKeyed upserts with retry.

Rows go to the sheet either way. The status column decides what gets paid.

Labels, not coordinates

A value is found right of its label, below it, or inside the same text run (Fattura n. 2026/0147). Line items are read from the right, so descriptions may contain numbers and wrap onto a second line.

The invoice checks itself

When a scan loses a decimal separator (15843), the value is repaired only if qty × price = amount then holds exactly, and the repair is written into the row's notes. A vendor's own arithmetic error is never corrected, only reported.

Two readers for scans

OCR and an LLM read the same page independently. Agreement is taken; disagreement is settled by the tax ID's check digit or the invoice's arithmetic; anything else goes to review as READERS_DISAGREE.

Test data

Every invoice is synthetic: fictional companies, generated tax IDs with real check digits, a seeded generator in the repo. A quarter of the documents are rasterised like an office scanner (150 dpi, skew, noise, JPEG). Some carry exactly one planted defect, so every detection can be scored. Hover to zoom.

A second reader, kept honest

{{llm_pages}} scanned pages that failed validation went to an LLM ({{llm_model}} via OpenRouter). On its own it read the currency symbols the OCR could not, and it also dropped a repeated digit from invoice numbers and tax IDs. One such invoice went to the sheet as “ok” with the wrong number: no business rule can see that.

READERS_DISAGREE invoice_number: OCR read '10597', LLM read '1059'

So the two readings are reconciled instead of replaced. A generic “two letters and digits” format match does not count as evidence: that loophole once let the model's CH76950391 beat a correctly flagged vendor typo, and a test now keeps it closed.

Crashes, retries, re-runs

The dangerous failure is not an error. It is a write that succeeded on the server whose response never arrived: a naive retry appends the rows twice. Here every retry re-reads the sheet's keys and updates in place.

Chaos test

The pipeline is killed with SIGKILL {{kills}} times at arbitrary moments and made to die {{crashes}} times right after a sheet write, before it can record it. The final sheets must equal a clean run, row for row. Replacing the upsert with a plain append makes the test fail.

Live Google Sheet

{{live_first}} invoices and {{live_lines}} line items written; a second run wrote nothing; every row re-sent through {{live_injected}} injected failures, {{live_lost}} of them lost responses after the write: all rows updated in place, none appended.

Re-processing

After a rules change the inbox can be processed again from scratch. Rows are updated by key; --prune removed the {{live_pruned}} rows whose key had changed, so the sheet never keeps a stale copy.

The live sheet

What the accounts-payable person opens. Amounts are written as numbers and dates as ISO text, so the spreadsheet's locale cannot turn 1.234 into a date.

Limits

  • Synthetic layouts, written by the same person as the rules. Real vendors bring logos, stamps, handwriting and multi-page tables.
  • One page per invoice; multi-page line tables are not handled.
  • One writer per spreadsheet.
  • Tax IDs are checked by check digit or format, not looked up in a registry such as VIES.
  • OCR runs on CPU, about six seconds per page, and drops £, €, some umlauts and many spaces.
  • The holdout numbers after fixes are on seen data; only the first-sight numbers are a test.
